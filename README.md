# PostgreSQL backup test

PostgreSQL 16 и S3-совместимое хранилище SeaweedFS.
Оба сервиса имеют healthcheck, restart: unless-stopped и ротацию логов: три файла по 10 МБ.

## Запуск

Нужны Docker, Compose v2+, Bash и AWS CLI v2.

~~~bash
cp .env.example .env
chmod 600 .env
~~~

Замените оба пароля в .env, затем выполните:

~~~bash
docker compose up -d --wait
bash ./backup.sh
bash ./restore.sh
~~~

S3 доступен на http://127.0.0.1:8333, PostgreSQL только внутри Docker-сети.
Данные сохраняются в volumes; down -v удалит их.
Файл .env является доверенным shell-файлом и исключён из Git вместе с дампами.

## Бэкап и восстановление

backup.sh создаёт сжатый дамп pg_dump -Fc, загружает его в S3 и после успешной загрузки удаляет копии старше 30 дней.
Возраст определяется по UTC-времени в имени; не переименовывайте объекты.
Очистка запускается вместе с успешным бэкапом, только для дампов этой базы ожидаемого формата.

restore.sh восстанавливает последний дамп во временную базу и проверяет контрольную запись из init.sql.
Исходная база не меняется, временная база и файлы удаляются при выходе.
Ошибки архива, SQL, данных или очистки возвращают ненулевой код; повреждённый последний дамп не заменяется старым.
После SIGKILL или недоступности PostgreSQL очистка может потребовать ручного вмешательства.

Нужно место для сжатого дампа и восстановленной базы с индексами.
Это smoke test: для Laravel уберите init.sql из Compose и задайте RESTORE_CHECK_SQL в .env, возвращающий одно true по бизнес-данным.
Рабочую базу восстанавливают отдельно через pg_restore в пустую базу.

## Расписание

Пример crontab с доступом к Docker, .env и записи логов:

~~~cron
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
0 * * * * /bin/bash /opt/postgres-backup-test/backup.sh >> /var/log/postgres-backup.log 2>&1
30 3 * * * /bin/bash /opt/postgres-backup-test/restore.sh >> /var/log/postgres-restore.log 2>&1
~~~

Настройте logrotate для этих логов и оповещения об ошибках и отсутствии свежего бэкапа.

## Проверка

На macOS/Colima прошли проверка Compose, bash -n, ShellCheck и 10 сценариев с настоящими PostgreSQL и S3, включая ошибки, retention и очистку временных данных.

## Ответы

### 1. Сервер умер. Как восстановить и сколько данных потеряем?

На новом сервере верну Docker, Compose, приложение, секреты и Laravel APP_KEY, скачаю исправный дамп из внешнего S3.
Восстановлю базу, проверю приложение, запущу nginx, очередь и планировщик.
Для небольшой базы ориентируюсь на 30–60 минут, точное время покажет репетиция.
При ежечасных успешных бэкапах потеряем примерно до часа данных; при сбоях отсчёт идёт от последнего исправного бэкапа.

### 2. Диск заполнен на 95%. Что делать?

Через df -h и df -i проверю место и inode, через du и docker system df найду источник роста.
Удалю ненужные временные файлы, старые логи и образы, сохранив нужное для отката.
Docker volumes, файлы PostgreSQL и WAL вручную удалять не буду; при необходимости приостановлю растущие задания.
Устраню причину, настрою ротацию и предупреждения на 80% и 90%, при необходимости расширю диск и проверю сервисы.

### 3. Как защитить бэкапы при взломе сервера?

Локальное S3 погибнет вместе с сервером, поэтому рабочие копии храню во внешнем хранилище отдельного аккаунта.
Серверу даю минимальные права загрузки, удаление поручаю lifecycle-политике без права менять её с сервера.
Versioning и Object Lock с retention защитят копии от удаления украденными серверными ключами.
Дампы шифрую публичным ключом до загрузки, приватный ключ и административный доступ храню вне сервера.
